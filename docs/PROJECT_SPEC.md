# Doomsday Ready --- Project Specification

## 1. Overview

Doomsday Ready is a small full-stack application for MCU fans who want
to prepare for *Avengers: Doomsday*. It helps users manage a list of
movies, work out which movies they should watch before a selected
target, and calculate an exact opening-night group booking using the
seat bundles offered by a cinema.

The application has three main areas:

1.  **Movies** --- create and manage movies and their prerequisites.
2.  **Rewatch Plan** --- generate an ordered list of prerequisite movies
    for a selected target.
3.  **Booking** --- calculate the smallest exact bundle combination for
    a group and save the result as a booking plan.

This is an assessment project, not a real cinema ticketing platform. It
will not process payments, reserve actual cinema inventory, or guarantee
seats.

## 2. Project goals

The main goals are to:

-   Implement the assessment requirements accurately.
-   Keep the two required algorithms as clear, hand-written,
    independently testable implementations rather than relying on
    libraries that solve the underlying problems.
-   Build a clean REST API and a usable React interface.
-   Use a data model that represents the relationships clearly.
-   Handle invalid input and important edge cases consistently.
-   Keep the project small enough to finish and explain confidently.

The application does not need authentication, payment integration,
real-time seat inventory, or an admin permission system.

## 4. Data model

The application will use three MongoDB collections: `movies`, `cinemas`,
and `bookings`.

### 4.1 Movie

A movie document represents one movie and the movies that should be
watched before it.

Suggested fields:

  -----------------------------------------------------------------------
  Field                   Type                    Rules
  ----------------------- ----------------------- -----------------------
  `_id`                   ObjectId                Generated by MongoDB

  `title`                 String                  Required; unique after
                                                  trimming and case
                                                  normalization

  `normalizedTitle`       String                  Internal value used for
                                                  case-insensitive
                                                  uniqueness

  `releaseYear`           Number                  Required positive
                                                  integer

  `runtime`               Number                  Required integer from 1
                                                  to 300 minutes

  `prerequisites`         ObjectId\[\]            References to other
                                                  Movie documents;
                                                  defaults to an empty
                                                  array

  `watched`               Boolean                 Defaults to `false`

  `createdAt`             Date                    Managed automatically

  `updatedAt`             Date                    Managed automatically
  -----------------------------------------------------------------------

Prerequisites are stored on the movie that depends on them. For example,
if The Avengers requires Iron Man, The Avengers contains Iron Man's ID
in its `prerequisites` array.

Rules:

-   A movie cannot reference itself.
-   A movie cannot participate in a direct or indirect circular
    dependency.
-   Prerequisite IDs must refer to existing movies.
-   The same prerequisite cannot appear more than once.
-   A movie title must be unique without treating differences in letter
    case or surrounding whitespace as different titles.
-   The target movie is never included in its own rewatch order.

### 4.2 Cinema

A cinema document stores the seat bundle sizes it offers for opening
night.

  -----------------------------------------------------------------------
  Field                   Type                    Rules
  ----------------------- ----------------------- -----------------------
  `_id`                   ObjectId                Generated by MongoDB

  `name`                  String                  Required; unique after
                                                  trimming and case
                                                  normalization

  `normalizedName`        String                  Internal value used for
                                                  case-insensitive
                                                  uniqueness

  `bundleSizes`           Number\[\]              Between 1 and 10
                                                  distinct integers; each
                                                  from 1 to 500

  `createdAt`             Date                    Managed automatically

  `updatedAt`             Date                    Managed automatically
  -----------------------------------------------------------------------

Rules:

-   Bundle sizes must be unique within a cinema.
-   The order in which bundle sizes are stored must not affect the
    optimal result.
-   A cinema must have at least one bundle size.

### 4.3 Booking

A booking document represents a saved booking plan produced by the quote
feature. It is not proof of a real cinema reservation.

  -----------------------------------------------------------------------
  Field                   Type                    Rules
  ----------------------- ----------------------- -----------------------
  `_id`                   ObjectId                Generated by MongoDB

  `cinema`                ObjectId                Reference to the Cinema
                                                  document

  `cinemaName`            String                  Snapshot of the cinema
                                                  name when the plan is
                                                  saved

  `groupSize`             Number                  Integer from 1 to
                                                  10,000

  `bundleSizes`           Number\[\]              Snapshot of the
                                                  cinema's bundle sizes
                                                  used for the quote

  `bundleBreakdown`       Object\[\]              Each entry contains
                                                  `size` and `quantity`

  `totalBundles`          Number                  Sum of bundle
                                                  quantities

  `totalSeats`            Number                  Sum of bundle size
                                                  multiplied by quantity;
                                                  must equal `groupSize`

  `status`                String                  Initially `saved`

  `createdAt`             Date                    Managed automatically

  `updatedAt`             Date                    Managed automatically
  -----------------------------------------------------------------------

A saved plan keeps a snapshot of the quote. If a cinema later changes
its bundle sizes or name, an older booking plan should still show the
values used when it was created.

The server must calculate the quote again when a booking is saved. It
must not trust a bundle breakdown or totals supplied by the frontend.

A booking can only be saved when an exact bundle combination exists.

## 5. Feature requirements

### 5.1 Movies

Users must be able to:

-   Create a movie.
-   View all movies.
-   Update a movie's title, release year, runtime, watched status, and
    prerequisites.
-   Mark a movie as watched or unwatched.
-   Choose prerequisites from existing movies.

Creation and updates must validate the full proposed dependency graph
before saving prerequisite changes.

If a create or update would introduce a circular dependency, the API
must reject it with:

-   HTTP status: `409 Conflict`
-   Error code: `CIRCULAR_DEPENDENCY`

A failed update must not leave partially changed prerequisite data.

Movie deletion is not part of the required assessment API. If deletion
is added, it should be rejected while another movie references the movie
as a prerequisite. Do not silently remove other movies' relationships.

### 5.2 Rewatch order

Endpoint:

`GET /api/movies/:id/rewatch-order`

The endpoint returns every transitive prerequisite of the target movie
exactly once, excluding the target itself.

The result must be a valid topological order: every prerequisite must
appear before a movie that depends on it.

The response must also include:

-   The target movie.
-   The ordered prerequisite movies.
-   Total number of prerequisite movies.
-   Number of prerequisite movies marked as watched.
-   Total runtime of prerequisite movies that are not watched.

Shared prerequisites must appear only once. A target with no
prerequisites returns an empty movie list and zero counts/runtime.

The implementation must use a hand-written graph traversal and must not
rely on a graph or topological-sort library.

### 5.3 Cinemas

Users must be able to:

-   Create a cinema.
-   List cinemas.
-   Provide between 1 and 10 distinct bundle sizes.
-   Edit cinema details if an update endpoint is added.

The API must validate bundle sizes before saving them.

### 5.4 Booking quote

Endpoint:

`GET /api/cinemas/:id/booking?groupSize=6`

Inputs:

-   A valid cinema ID.
-   A group size from 1 to 10,000.

The response must provide the minimum number of bundles whose seat
counts add up to exactly the requested group size, plus the quantity of
each bundle size used.

If no exact combination exists, return a successful quote response with
`possible: false`. This is a valid business result, not a server error.

The implementation must use a hand-written dynamic programming solution.
Do not use a coin-change, knapsack, or optimization library.

When more than one combination uses the same minimum number of bundles,
use a consistent tie-breaking rule. Prefer the combination containing
the larger bundle at the first point of difference. Sort bundle sizes in
descending order when evaluating candidates so the behavior is
predictable.

### 5.5 Saved booking plans

Additional endpoints:

-   `POST /api/bookings` --- calculate and save a booking plan.
-   `GET /api/bookings` --- list saved booking plans.

The create endpoint should accept only the cinema ID and group size as
business inputs. The backend must load the cinema, calculate the optimal
combination, and store a snapshot of the result.

If no exact combination exists, do not create a booking document.

## 6. API contract

All endpoints are under `/api`.

  Method   Path                                 Purpose
  -------- ------------------------------------ ----------------------------------
  POST     `/movies`                            Create a movie
  GET      `/movies`                            List movies
  PATCH    `/movies/:id`                        Update a movie
  GET      `/movies/:id/rewatch-order`          Get the prerequisite watch order
  POST     `/cinemas`                           Create a cinema
  GET      `/cinemas`                           List cinemas
  GET      `/cinemas/:id/booking?groupSize=6`   Calculate a booking quote
  POST     `/bookings`                          Save a booking plan
  GET      `/bookings`                          List saved booking plans
  GET      `/health`                            Health check

The API should use a consistent response envelope:

Successful response:

``` json
{
  "success": true,
  "data": {}
}
```

Error response:

``` json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The supplied data is invalid."
  }
}
```

Use appropriate HTTP status codes:

-   `200` for successful reads and updates.
-   `201` for successful creation.
-   `400` for invalid request data.
-   `404` for missing resources.
-   `409` for duplicate names and circular dependencies, with distinct
    error codes.
-   `500` for unexpected server errors.

Do not expose stack traces, database credentials, or internal error
details in production responses.

## 7. Algorithm requirements

### 7.1 Circular dependency detection

Model the prerequisite relationships as a directed graph. An edge from a
movie to one of its prerequisites means that the prerequisite must be
watched first.

Before saving a proposed dependency change:

1.  Load the relevant movie relationships.
2.  Apply the proposed change to an in-memory representation of the
    graph.
3.  Run cycle detection using a hand-written depth-first search (DFS).
4.  Reject the change if a cycle exists.
5.  Save only after validation succeeds.

The algorithm must detect both direct and indirect cycles. Its expected
complexity is `O(V + E)` for a graph with V vertices and E edges.

### 7.2 Rewatch ordering

Use DFS with a visited set so shared prerequisites are included only
once. Add a prerequisite to the result after visiting its own
prerequisites. This produces a valid prerequisite-first order.

The expected complexity is `O(V + E)` for the reachable portion of the
graph.

### 7.3 Minimum-bundle calculation

Use bottom-up dynamic programming.

For a requested group size `G`, maintain:

-   A minimum-bundle-count array.
-   A choice array that records which bundle size produced the best
    result.

For each seat total from 1 through G, examine each available bundle size
that does not exceed the current total. Update the best count and
choice.

If the target remains unreachable, return `possible: false`. Otherwise,
reconstruct the bundle quantities by following the recorded choices.

Expected complexity:

-   Time: `O(G * B)`.
-   Space: `O(G)`.

Here, B is the number of bundle sizes, with a maximum of 10.

These algorithms must remain direct implementations of the required
DFS and dynamic programming approaches. AI tools may assist with writing
code, but the project owner is responsible for reviewing the
implementation, understanding how it works, validating it with tests,
and being able to explain the approach and its complexity. General-
purpose libraries may be used elsewhere, but not to solve these two
assessment problems.

## 8. Frontend requirements

The React application will have three main views.

### 8.1 Movies

-   Show the movie list.
-   Provide a form or dialog to add a movie.
-   Allow editing movie details and prerequisites.
-   Provide a watched/unwatched control.
-   Show validation and API errors clearly.
-   Prevent selecting the movie itself as its prerequisite.

### 8.2 Rewatch Plan

-   Allow the user to select a target movie.
-   Request the rewatch order from the backend.
-   Display movies in the returned order.
-   Show watched indicators.
-   Display progress, such as `4 of 7 watched`.
-   Display the remaining runtime of unwatched movies.
-   Handle an empty prerequisite list and loading/error states.

The backend is the source of truth for the order and calculations.

### 8.3 Booking

-   Allow the user to select a cinema.
-   Accept a group size from 1 to 10,000.
-   Request and display the booking quote.
-   Show the minimum bundle count and quantity of each bundle.
-   Show a clear message when an exact combination is impossible.
-   Allow a possible quote to be saved as a booking plan.
-   Show previously saved plans.

Make it clear that saving a plan does not reserve actual cinema seats.

### 8.4 Visual direction

Use a dark cinematic visual direction with restrained red accents. The
landing/header area can have a stronger cinematic feel, while the actual
dashboard views should remain clean and easy to use.

The interface must be responsive and should include useful loading,
empty, success, and error states. Avoid decorative elements that make
the core tasks harder to use.

## 9. Data integrity and deletion behavior

-   Use unique indexes for normalized movie titles and cinema names.
-   Validate referenced movie and cinema IDs.
-   Prevent duplicate prerequisite references and duplicate bundle
    sizes.
-   Validate a proposed graph before persisting it.
-   Use appropriate atomic database operations or transactions where
    multiple writes are required.
-   Do not delete a movie while another movie references it as a
    prerequisite.
-   Do not delete a cinema while saved booking plans reference it.
-   Do not silently cascade-delete related records.

MongoDB Atlas transactions should only be introduced if the
implementation genuinely needs multi-document atomicity. If transactions
are used, the Atlas deployment must support them.

## 12. Out of scope

Do not add these features unless there is a clear assessment-related
reason:

-   User authentication and authorization.
-   Payment processing.
-   Real cinema seat inventory.
-   External cinema booking integration.
-   Email or SMS notifications.
-   Movie metadata APIs.
-   Complex admin roles.
-   Real-time updates.
-   Microservices.
-   Redis or message queues.

## 13. Definition of done

The project is ready for submission when:

-   The frontend and backend can be started using documented commands.
-   The backend connects to MongoDB Atlas using environment variables.
-   Movie and cinema CRUD requirements work.
-   Direct and indirect circular dependencies are rejected with the
    required error code and status.
-   Rewatch ordering returns each prerequisite once in a valid order.
-   Watched counts and unwatched runtime are correct.
-   Booking quotes return a minimum exact bundle combination or
    `possible: false`.
-   Saved booking plans preserve the quote snapshot.
-   The three frontend views work against the API.
-   Important validation and algorithm cases have automated tests.
-   The README explains setup, data models, algorithms, API usage, and
    AI assistance accurately and concisely.
